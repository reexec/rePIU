## rePIU v0.0.229

이전 릴리스 **v0.0.228** 이후의 변경입니다. **브라우저 페이지가 CHD를 한 번만 풀고, 60fps로 묶이며, OSD에 FPS 그래프가
생겼습니다.** 배포 빌드(Windows·Linux)에서 바뀐 것은 OSD의 FPS 그래프뿐입니다.

### 반영된 issue

| issue | 내용 | PR |
|---|---|---|
| [#86](https://github.com/reexec/rePIU/issues/86) | 웹: 푼 게임 파일을 브라우저 저장소(OPFS)에 남겨 CHD는 한 번만 풂 | [#89](https://github.com/reexec/rePIU/pull/89) |
| [#87](https://github.com/reexec/rePIU/issues/87) | 웹: 브라우저 빌드의 프레임을 60fps로 묶음 | [#89](https://github.com/reexec/rePIU/pull/89) |
| [#88](https://github.com/reexec/rePIU/issues/88) | OSD 오른쪽 위에 현재 FPS와 최근 60초 그래프 | [#89](https://github.com/reexec/rePIU/pull/89) |

### 바뀐 것

* **푼 파일 저장(#86):** 처음 시작할 때 CHD에서 푼 파일(약 410 MB)을 게임이 도는 동안 브라우저 저장소에 남깁니다. 같은 CHD로
  다시 시작하면 풀기를 건너뛰어 첫 화면까지 약 92초 → 약 36초. 페이지에 저장 상태와 "Clear saved files" 버튼이 있습니다.
* **60fps 상한(#87):** 브라우저에서 화면 교체가 초당 60을 넘지 않습니다. 가벼운 장면이 100~300fps로 돌던 것이 60으로
  묶이고, 60 아래의 장면은 느려지지 않습니다. 네이티브의 vsync·페이서와 같은 기한 규칙입니다.
* **OSD의 FPS(#88):** OSD 오른쪽 위에 현재 FPS, 최근 60초 그래프(60fps 기준선, 눈금과 바깥의 눈금 글자), 최저·평균·최고.
  OSD를 닫아 둔 동안에도 기록합니다. 네이티브와 브라우저 모두.
* **진단:** 페이지 주소의 `REPIU_*` 매개변수가 엔진 환경 변수가 됩니다(예: `index.html?REPIU_GLIDE_FRAME_RATE_LOG=1`).

### 확인한 것

| 구성 | 확인 |
|---|---|
| 브라우저(headless Chrome) | 같은 프로필 두 번째 시작에서 풀기 생략, 가벼운 장면 60.0fps(이전 최대 326), OSD의 FPS 그래프 |
| Win32 Release | OSD의 FPS 그래프 캡처, glide render probe |
| Win32 Debug·Release·`emulated`, Linux x64·i386, 웹 Node | 빌드, core probe(새 `frame_rate_history` 포함) |

### 알려진 것

* 게임이 쓰는 `nvram`·`cfg`는 브라우저에서 여전히 실행마다 처음부터입니다.
* 사용자 브라우저(실제 화면 주사율)에서의 확인이 남았습니다.
* Win32 Release 실행 한 번이 시작 직후 게스트 예외로 끝났습니다. 바로 이은 실행들에서는 재현되지 않았고 원인은 모릅니다(#88 작업
  로그).

## rePIU v0.0.229

Changes since **v0.0.228**. **The browser page unpacks the CHD once, is held to 60 fps, and the OSD gains a frame rate
graph.** In release builds (Windows, Linux) only the OSD's frame rate graph is new.

### Issues addressed

| issue | Summary | PR |
|---|---|---|
| [#86](https://github.com/reexec/rePIU/issues/86) | Web: keep the unpacked game files in the browser's storage (OPFS) so the CHD is unpacked once | [#89](https://github.com/reexec/rePIU/pull/89) |
| [#87](https://github.com/reexec/rePIU/issues/87) | Web: hold the browser build's frames to 60 fps | [#89](https://github.com/reexec/rePIU/pull/89) |
| [#88](https://github.com/reexec/rePIU/issues/88) | The current FPS and a graph of the last 60 seconds at the OSD's top right | [#89](https://github.com/reexec/rePIU/pull/89) |

### Changed

* **Saved unpacked files (#86):** the first start keeps the files unpacked from the CHD (about 410 MB) in the browser's
  storage while the game runs. Starting again with the same CHD skips the unpack, and the first picture comes in about
  36 s instead of about 92 s. The page shows what is saved and has a "Clear saved files" button.
* **60 fps cap (#87):** in the browser the swaps never exceed 60 a second. Light scenes that ran at 100–300 fps are held
  to 60, and scenes under 60 do not slow down. The deadline rules are the native vsync pacer's.
* **FPS in the OSD (#88):** at the OSD's top right, the current rate, a graph of the last 60 seconds (a 60 fps reference
  line, a scale, and its labels outside), and the low, mean and high. Recorded while the OSD is closed too. Native and
  browser alike.
* **Diagnosis:** `REPIU_*` parameters in the page's address become the engine's environment variables
  (`index.html?REPIU_GLIDE_FRAME_RATE_LOG=1`, for one).

### Checked

| Configuration | Check |
|---|---|
| Browser (headless Chrome) | the unpack skipped on the second start with one profile, light scenes at 60.0 fps (up to 326 before), the OSD's frame rate graph |
| Win32 Release | a capture of the OSD's frame rate graph, the glide render probe |
| Win32 Debug, Release and `emulated`, Linux x64 and i386, web under Node | build, core probe (with the new `frame_rate_history`) |

### Known

* The game's `nvram` and `cfg` still start afresh on every run in the browser.
* A check in the user's browser (at the real display rate) is still to do.
* One Win32 Release run ended right after start on a guest exception; it did not come back in the runs straight after,
  and the cause is unknown (#88's work log).
